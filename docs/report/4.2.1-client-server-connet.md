# Client-Server Connection and Communication Flow

This front-end application is designed as a guided floor-plan workspace rather than a simple form-based interface. Its main responsibility is to collect land information, help the user shape a buildable plot, submit design requirements to the server, and then present the generated floor plan in a clear visual format. The most important idea behind the client is that it does not perform the heavy generation work itself. Instead, it acts as the interactive controller that prepares user input, sends it to the backend, follows the progress of long-running jobs, and translates the returned geometry into an understandable drawing on the canvas.

The user experience begins on the landing page, which introduces the project and directs the user into the workspace. From there, the client switches into a two-stage design flow. In the first stage, the user defines the land boundary and adjusts the plot shape. The interface allows the points of the polygon to be moved, added, or removed within a controlled limit. The client also supports area scaling so that the user can match the land shape to a target measurement before sending any request to the server. This is important because the backend generation process depends on realistic plot dimensions. At this stage the client keeps the work local, providing instant visual feedback so the user can refine the site without waiting for network responses.

The next major feature is road placement and buildable-space evaluation. Once the plot boundary is confirmed, the user may place a road connection on the land edge. The client then packages the boundary geometry and road information into a buildable-space request. This request is sent to the server to determine the usable rectangle inside the plot after applying setbacks and other spatial rules. The backend responds asynchronously, meaning the request is accepted immediately while the computation continues in the background. The client listens for updates through the job lifecycle rather than freezing the interface. This design is essential for a computationally expensive system because it keeps the application responsive while still handling large spatial calculations.

After the buildable-space response arrives, the client uses the returned geometry to guide the next stage: room configuration. The user opens the room selection dialog and chooses the required interior spaces, such as bedrooms, kitchen, bathrooms, and optional rooms. The client also lets the user set the overall floor dimensions within the limits derived from the buildable area. This step is not just a simple form submission; it is a validation layer that helps the user prepare a feasible request before the floor-plan generator runs. The interface checks whether the proposed arrangement is likely to fit the available land and provides feedback such as whether the request is good, tight, or impossible. This is a useful research-oriented feature because it reduces invalid submissions and improves the quality of the interaction between the user and the server.

When the room requirements are submitted, the client sends a floor-plan generation request to the backend. The payload includes the floor dimensions, aspect ratio, and the room template. This request starts the main asynchronous generation job. The server immediately returns a job identifier, which becomes the reference for all future communication about that task. The client does not wait for the final plan in the same response. Instead, it treats the job ID as the beginning of a longer conversation with the backend. This pattern is well suited to optimization and search-based algorithms because those algorithms may run through multiple internal trials before producing a stable result.

The communication flow after submission is the most important part of the architecture. The client subscribes to real-time server events using a streaming channel and also keeps the ability to query the job status directly. The event stream provides progress updates such as job start, layout generation, refinement passes, scoring, and completion. These updates help the user understand that the system is working even when the final answer is still being computed. If the stream is interrupted or if the application needs confirmation, the client can poll the status endpoint to retrieve the current state and any stored result. This combination of streaming and polling makes the experience reliable in different network conditions.

The server communication model is also session-aware. Every request carries a persistent client identifier stored in the browser, which allows the backend to associate jobs and progress with the same user session. This is especially useful when multiple jobs are started or when the page is refreshed during a long operation. The client can then restore context and continue tracking the same workflow instead of starting from zero. The application also includes a cancellation path so the user can stop a running job when the chosen inputs are no longer needed. That is a practical feature in a design tool, because users often change dimensions or room requirements before the computation finishes.

Once the backend returns the final floor-plan result, the client converts the raw response into canvas-ready geometry. The generated output contains walls, room polygons, room labels, and openings such as doors or windows. The client then prepares these elements for display by translating them into lines, labels, and markers that the drawing layer can render efficiently. This transformation is important because the backend speaks in terms of planning data, while the front end must speak in terms of visual presentation. The client bridges that gap by turning the structured result into a clear architectural preview.

Another important communication detail is unit handling. The land and room inputs are entered in user-friendly measurements, while some backend responses are returned using a different scale. The client normalizes these values before drawing so that the visual preview remains proportionally correct. Without this step, the diagram would not match the intended dimensions and the preview would become misleading. The same principle applies to room labels, openings, and wall segments: the application prepares each element in a consistent form so the canvas can draw everything in the correct position.

In practical terms, the front end therefore serves three functions at once: it is a planner, a messenger, and a presenter. As a planner, it helps the user define the land and room requirements. As a messenger, it communicates with the backend using asynchronous jobs, progress events, status checks, and cancellation requests. As a presenter, it converts the final layout into a readable floor-plan visualization. This separation of responsibilities is valuable for a final-year project because it demonstrates a clean division between user interaction and backend computation.

Overall, the client-server connection in this project is built around responsiveness, traceability, and clarity. The user can make changes locally, submit only meaningful requests, observe the server’s progress in real time, and review the generated plan without needing to understand the internal algorithmic details. This makes the application suitable for both practical use and research presentation. The communication flow is not just a technical implementation detail; it is a core part of the user experience because it determines how confidently the user can move from an abstract land boundary to a concrete architectural result.
